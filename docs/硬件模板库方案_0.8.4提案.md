## 2. 现状事实（可逐条核对）

### 2.1 "插入模板"按钮不在实际编辑路径上

| 位置 | 事实 |
|---|---|
| `Program.cs:73` | `ActionDialog` 只在这里被调用，命令是 `--render-actions`（生成截图） |
| `Editor.cs:131` | 实际编辑走 `PhaseDialog`，不是 `ActionDialog` |
| `PhaseTools.cs:33` | `PhaseDialog` → `ActionProperties`（`PhaseTools.cs:74`） |
| `PhaseTools.cs:74–78` | `ActionProperties` 只有 5 个文本框：公共头文件 / 启动一次 / 完成条件 / 完成清理 / 取消清理，**无预设、无插入按钮** |

写回 `document.ActionIncludes`）已经通了，所以只加 UI 和数据。

### 2.2 动作钩子只在动作窗口内生效

`ActionStart / ActionCondition / ActionDone / ActionCancel` 每次进入航点动作才运行一次。
且 `ActionIncludes` 只被写成 `rcs_actions.c` 的 `INCLUDES_REGION`（`TemplateGenerator.cs:79`），
**到不了 `app.c` / `rcs_app_task.c`**。

含义：传感器放进去，语义会变成"执行机构动作时才采陀螺仪"，位置错误。

### 2.3 传感器已经有家

| 位置 | 事实 |
|---|---|
| `CorrectionEditor.cs:29` | `HardwareDialog` 已存在：档案列表 + PropertyGrid + 导入/删除 |
| 定位硬件档案 | 字段 `Kind` / `Axes` / `DriverHeader` / `ReadFunction` / `MapAligned` / `BindingReady` |
| `examples/foxmolika_observation_adapter.c` | `TeamGps_ReadObservation` 目前 `return 0`，是空壳 |

### 2.4 可用的生成期插入点

| 区域 | 文件 | 用途 |
|---|---|---|
| `APP_INCLUDES`（**新增**） | `rcs_app_task.c` 顶部 | `#include "rcs_hw_config.h"` |
| `APP_TICK` | `rcs_app_task.c`（每个周期） | 传感器 `process()` 调用 |
| `APP_CONTEXT` / `APP_ON_STATE` / `APP_FAULT_ENTER` | `rcs_app_task.c` | 状态相关钩子 |
| `RCS_ACTION_INCLUDES` | `rcs_actions.c` | 执行器头文件 |
| 5 个文本框 | 地图 JSON 的 `ActionIncludes` / `ActionStart` 等 | 执行器调用片段 |

`APP_INCLUDES` 是这次唯一要改模板的地方（`rcs_app_task.c.tpl` 顶部加三行标记）。
不选硬件时它保持为空，因此现有 19 文件的输出逐字节不变；共享静态头（如
`rcs_app_config.h`）不做任何修改。

## 3. 两个入口

| 类别 | 入口 | 写到哪里 | 例子 |
|---|---|---|---|
| **执行器** | `ActionProperties` 新增设备下拉 + 插入按钮 | 5 个文本框 → 地图 JSON | 气缸、舵机、夹爪、升降、6020 转台 |
| **传感器 / 通信** | `HardwareDialog` 新增"从设备模板新建"下拉 | 预填一条 `HardwareSource` + `APP_TICK` 一行 `process()` | 陀螺仪、编码器、遥控、激光、GPS |

### 3.1 执行器为什么适合动作钩子

气缸、舵机、升降本身就在"到点 → 伸出 → 等到位 → 停留"的窗口里工作，
`ActionStart` / `ActionCondition` / `ActionDone` 正好是这三个时点。

### 3.2 传感器为什么必须走档案

陀螺仪要每个周期喂数据，遥控要随时可接管，编码器要连续积分。
它们的位置是：`APP_TICK` 每周期 `process()` + 中断里 `on_rx()` + 定位硬件 `ReadFunction` 取数。

### 3.3 两个入口不能合并

合并只会导致两种情况：把传感器塞进动作（语义错），或把执行器塞进全程轮询
（机构在航点之间乱动）。这不是折中问题，是模型不匹配。

### 4.4 插入策略：注释还是真代码

现在的三预设**故意全插注释**（`/* Gripper_Start(); TODO */`），这是 README 的承诺：
"不能靠任意占位函数称为已经适配"。复选框化后按 `verified` 分级：

| `verified` | 插入内容 | 界面文案 |
|---|---|---|
| `none` | 注释形态：`/* hw_cylinder_extend();  需 GPIO + 到位检测，见 rcs_hw_config.h */` | 灰色"未验证" |
| `host` | 可执行调用 + `/* 仅主机回归，未实车 */` 注释 | 黄色"主机验证" |
| `hardware` | 可执行调用 | 绿色"实车验证" |

这样"方便调用"和"不假装适配"同时成立。

## 5. 自动交付与登记

### 5.1 目录约定

```
<工程根>/
  Application/
    foxmolikaRoute/          # 既有：19/21 个生成文件
    foxmolikaHardware/       # 新增：勾选的驱动 .c/.h
      rcs_hw_config.h        # 新增：由选择生成的配置与 #error 检查
      hardware.xml           # 本次交付记录
```

`rcs_hw_config.h` **只在至少选中一个设备时**生成，放在该目录（自动落在 IncludePath 里）。
`rcs_app_task.c.tpl` 顶部新增一个 `USER CODE BEGIN APP_INCLUDES` 区，插入
`#include "rcs_hw_config.h"`。不选任何设备时该区为空，**生成结果与 0.8.3 逐字节相同**，
也不去动 `rcs_app_config.h` 这种全工程共享的静态头。

`USER CODE` 区不是 `SourceTemplates.Slots` 管理的模板块（模板块是 `/* RCS TEMPLATE … */`），
所以新增一个 `USER CODE` 区不需要改 `SourceTemplates`，只需给 `.tpl` 加三行标记。

**为什么不放进 `foxmolikaRoute`**：`RequiredRouteFiles` 按文件名计数判断 19/21 完整性，
混入额外文件会让完整性判定和 `UpdateRoute` 的"多余文件移除"逻辑变复杂；分开目录互不干扰。

### 5.2 交付流程

```
1. 用户勾选设备（执行器在动作对话框、传感器在定位硬件对话框）
2. 从内嵌资源读出该设备的 .c/.h 字节
3. 计算目标路径，检查是否已存在
4. 全部文件与 uvprojx 变更先算完 → 无冲突才提交（任一失败不写，对齐现有导出事务语义）
5. 写文件（ProjectBinding.AtomicWrite：临时文件 + 校验 + 重试 + 拒绝软链接）
6. 登记 uvprojx：新增 Group「Application/foxmolikaHardware」+ IncludePath
7. 写 hardware.xml 记录设备 id、文件 SHA256、模板版本、时间
8. 重新生成 rcs_hw_config.h（宏、`#error`、`#include`）；一个设备都没选时不生成，
   此前生成过的由生成器删除（它是生成产物，不受 5.4 的"保留用户文件"规则约束）
```

### 5.3 登记算法

镜像现有 `ProjectBinding.UpdateRoute`（`ProjectBinding.cs:301`），新增 `UpdateHardware`：

| 事项 | 做法 |
|---|---|
| 目标工程筛选 | 与现有一致：含 `rcs_chassis.c` 的 `Target` 才动 |
| 分组名 | `Application/foxmolikaHardware`（与 `RouteRelative` 同风格） |
| 文件类型 | `.c` → `FileType=1`，`.h` → `FileType=5`（沿用现有约定） |
| IncludePath | 追加该目录，已存在则不重复 |
| 幂等 | 按 `FileName` + `FilePath` 比对，重复导出不重复登记 |
| 冲突保护 | 同名文件指向别的目录 → 报错，不覆盖 |

### 5.4 覆盖 / 回滚 / 取消

| 情况 | 处理 |
|---|---|
| 文件不存在 | 写入 |
| 已存在且内容相同 | 跳过 |
| 已存在且与 `hardware.xml` 记录的 SHA256 一致 | 覆盖（视为我们写的） |
| 已存在但用户改过（hash 不符） | **拒绝**，提示"该文件已被修改，请先备份或移除" |
| 提交中途失败 | 全量回滚，不留半套文件 |
| 取消勾选 | 从 Group 移除登记、该目录无其他设备时移除 IncludePath；设备 `.c/.h` **保留**并提示可手动删除；`rcs_hw_config.h` 由生成器重写或删除 |

### 5.5 记录文件为什么不能写进 `.foxmolika-project.xml`

`ProjectBinding.cs:250–253` 对该文件做了严格校验：

```csharp
xml.Elements().Any()   // 有任何子元素 → 判定不兼容
xml.Attributes().Any(a => !new[]{"Schema","Ioc","ProjectName","RouteDirectory"}.Contains(...))
```

也就是说**加一个 `<Hardware>` 子节点会让所有旧工程的关联记录判为不兼容**。
所以硬件记录单独放 `Application/foxmolikaHardware/hardware.xml`，
`.foxmolika-project.xml` 一个字节都不动。

## 6. 冲突兜底（编译期）

### 6.1 生成的 `rcs_hw_config.h`

```c
/* 由设备选择生成；改这里会被下次导出覆盖 */
#pragma once

#define RCS_HW_UART_GYRO      3
#define RCS_HW_UART_REMOTE    3
#define RCS_HW_MOTOR_CAN      1
#define RCS_HW_LASER_ENABLED  0

/* 两个设备抢同一 USART */
#if RCS_HW_UART_GYRO && RCS_HW_UART_GYRO == RCS_HW_UART_REMOTE
#error "RCS: 陀螺仪与遥控不能共用同一 USART"
#endif

/* 硬件电机模块与底盘抢 0x200 电流槽 */
#include "rcs_config.h"
#if RCS_HW_MOTOR_CAN && RCS_HW_MOTOR_CAN == RCS_CAN_BUS
#error "RCS: 硬件电机模块与底盘使用同一 CAN 与 0x200 发送槽"
#endif

#include "hw_wit_gyro.h"
```

风格与现有 `rcs_config_h.ftl` 的 `#error` 检查一致（`pack/CubeMX/templates/rcs_config_h.ftl:20`）。

### 6.2 能覆盖 / 覆盖不了

| 冲突 | 能否抓到 |
|---|---|
| 两个模板抢同一 USART | 能（`#error`） |
| 模板与底盘抢 `0x200` | 能（`#error`） |
| 两个模板抢同一 TIM 通道 | 能（`#error`） |
| 模板与用户手写代码抢资源 | **不能**（生成器看不见手写代码） |
| 同一设备要两份实例 | **不能**（本方案不做参数化） |

第 4 条是本方案的已知缺口，界面要写明"仍需自行核对外设占用"。

## 8. 验收标准

1. 动作对话框选中"气缸"→ 5 个文本框按片段填入；`verified=none` 的条目只插注释。
2. 定位硬件对话框选"维特陀螺仪"→ 生成一条 `HardwareSource`，`Kind=imu`、`Axes=4`、
   `DriverHeader`/`ReadFunction` 已填，`MapAligned`/`BindingReady` 仍为 false。
3. 勾选后导出：`Application/foxmolikaHardware/` 出现对应 `.c/.h`，uvprojx 新增分组并登记，
   IncludePath 含该目录；再次导出不重复登记。
4. 手改一个 `.c` 后重新导出 → 拒绝覆盖并提示，不静默丢改动。
5. 取消勾选 → 登记移除、文件保留、提示可手动删除。
6. 两个设备填同一 `RCS_HW_UART_*` → 编译期 `#error`，文案指名两个设备。
7. 底盘用 CAN1 + 选 CAN1 电机模块 → 编译期 `#error`（抢 `0x200`）。
8. `check.py --level host`、`GeneratedPolicy`、19/21 文件完整性判定均不受影响。
9. **不选任何设备时，19/21 文件的生成结果与 0.8.3 逐字节相同**（`APP_INCLUDES` 区为空，
   不生成 `Application/foxmolikaHardware/`）。这是批 2 的回归基线。

## 9. 风险与对策

| # | 风险 | 对策 |
|---|---|---|
| 1 | 插入片段但文件没复制 → 编译失败 | 批 2 的自动复制是必需项，不做 (a) 手动方案 |
| 2 | 用户改了交付文件，被下次覆盖 | SHA256 比对，不符就拒绝（5.4） |
| 3 | `hardware.xml` 与 uvprojx 不一致（用户手工删了登记） | 导出时以 uvprojx 为准重建登记，xml 只作记录 |
| 4 | 传感器 `process()` 插错位置 | 只允许写 `APP_TICK`；`APP_CONTEXT` 等区域不开放给模板 |
| 5 | 片段里出现 `USER CODE` 保留标记 | 复用现有校验（`ActionDialog.Save` / `UserRegions.Block` 同一套判断） |
| 6 | 驱动源文件 GBK / UTF-8 混编 | 新模板统一 UTF-8；STD 库文件不直接进包 |
| 7 | 未实车驱动被当成已适配 | `verified` 三态 + 界面颜色 + 插入内容分级（4.4） |
| 8 | 设备清单膨胀，维护成本上升 | `devices.json` 单文件索引；每设备必须有真实源文件与 `verified` 字段 |
| 9 | 模板新增 `USER CODE` 区，老工程重新导出时的合并 | 默认正文为空、只增不减；用现有 Seal/Merge 回归用例覆盖（`WorkspaceTests` / `test_export_transaction`） |
| 10 | 升级后 `hardware.xml` 里的旧 SHA256 与新交付文件不匹配 | 记录里带模板版本号；版本不一致时提示重新勾选，不静默覆盖 |

## 10. 附录 A：L3 完整方案（暂不做）

修订 1 的完整设计仍然有效，触发条件如下——满足任意一条再启动：

- 需要**同一设备多实例**（两路陀螺仪、四路激光）；
- 需要**参数化生成**（引脚/波特率/方向由界面填，生成器写进代码而不是靠手改 `rcs_hw_config.h`）；
- 需要**生成期资源占用表**（要在写文件前拦住冲突，而不是编译期 `#error`）；
- 需要**FreeRTOS / 旧标准库工程**支持（修订 1 的 5.2 / 5.3 节）。

届时的主要增量仍是：manifest 加载器、参数化模板、`owns` 资源键、`UpdateHardware` 扩展到
冲突判定、双模式测试矩阵。
