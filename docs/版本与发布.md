# 版本与发布

当前版本唯一来源为 `tools/version.py`。运行 `python tools/sync_versions.py` 同步C#常量与当前HTML教程；HTML源位于 `docs/templates/*.html.in`。历史迁移白名单、基线和旧发布报告保留原版本。构建缓存及验收报告写入忽略的build/dist目录。

开发时可在工作区运行 `python tools/check.py --level host`；`--level native` 再追加实际CubeMX生成、安装和Keil编译。正式发布使用 `--level release`，除native工具外，还要求维护者事前保存的历史目录及SHA256快照。没有旧资产证据时不会跳过该项。

若原生工具装在自定义目录，可在运行验收前设置 `STM32CubeMX_PATH` 为 CubeMX 安装目录，设置 `RCS_KEIL_UV4` 为 UV4.exe 的完整路径。

正式发布顺序如下：

1. 完成代码、版本、文档和发布脚本修改，提交并冻结本次候选版本；确认远端不存在该版本，再创建本地候选tag。已公开tag不得移动。
2. 从该tag创建独立的干净工作区，例如 `git -c core.autocrlf=false worktree add --detach ../Cubemx_RCS_release_0.8.2 v0.8.2`。维护者只复制旧资产的核验快照，不复制旧native通过记录。
3. 在该目录运行 `python tools/check.py --level release`。开始时记录commit、tree、版本、ASCII资产清单及所有Git源码摘要；每个步骤前后确认工作区仍干净、HEAD与tag均未改变。修改过源码或脚本必须完整重新验收，不能沿用旧报告。
4. 最后打包只读取当前通过的产物。源码ZIP由Git归档生成，附BUILD_PROVENANCE.json；逐字节核验文件集合与内容。独立Provenance附件、Validation附件及check-release记录必须使用同一来源。
5. 完整门禁通过后，推送源码和这个新tag；运行 `python tools/publish_release.py` 做只读预检，再显式运行 `python tools/publish_release.py --publish`。发布器解析远端真实tag提交，先上传草稿并逐项核对名称、大小、SHA256，全部通过才公开。已公开同版本拒绝覆盖。
6. 保存build/github-publication.json回执并检查Release，再从公开下载地址下载安装器比对SHA256。SHA256SUMS覆盖正式附件；发布前后核对旧v0.8.0和v0.8.1的标签及资产未变。用户可运行 `Get-FileHash .\foxmolika_CubeMX_Setup_0.8.2_win-x64.exe -Algorithm SHA256` 与清单比对。

若只有最终打包步骤失败，可用 `--level release --from tools/release.py` 续跑，但必须保留同一来源记录及完整前序通过清单；跨提交续跑会被拒绝。旧 `release_080.py` 仅作为当前打包脚本的兼容入口。

0.8.2使用独立安装目录和foxmolika_Tools_082。重新关联时，仅允许哈希匹配的官方旧助手迁移；保留旧目录，未知自定义助手需要手动合并。升级工程请显式重新关联、Generate并重载Keil。

v0.8.1曾在发布完成后才提交资产命名脚本，导致源码包与发布命名行为不一致。该历史缺口如实保留，v0.8.2改为上述流程。旧v0.8.0/v0.8.1标签和附件不修改。若新版本公开后发现错误，发布更高补丁版本说明修正，不移动已公开标签。来源一致性并不代表跨工具链的EXE可逐字节复现。

文件操作诊断：目录重命名只对5/32/33作有限重试；原子File.Replace另处理已复现的1175（ERROR_UNABLE_TO_REMOVE_REPLACED），每次前提是目标和暂存快照未变化。1176/1177等不盲目重试。持续拒绝仍退出，错误保留路径、次数、HRESULT及清理原因。

每份新报告绑定本次产物哈希，旧报告只证明旧资产未变化。Keil原始日志可能含许可证信息，仅留忽略目录。历史固件比较仅规范Git的CRLF/LF差异；新pack与本次源文件仍逐字节一致。未烧录、未实车测试，不将同机隔离用户配置称作第二台物理电脑验收。
