# 版本与发布

日常改动先跑 host。准备新版本时，从干净的候选标签运行 release。通过后会生成一个冻结的发布候选，GitHub 发布器只读取该候选。

| 命令 | 用途 |
| --- | --- |
| python tools/check.py --level host | Windows 主机回归、编辑器和 pack 构建 |
| python tools/check.py --level native | 追加真实 CubeMX 安装、生成、再生成、Keil 编译和卸载 |
| python tools/check.py --level release | 按同一候选标签执行全部检查，并冻结待发布资产 |
| python tools/check.py --level release --list | 查看步骤，不启动验收 |
| python tools/publish_release.py | 本地核对冻结候选、标签、源码包和附件哈希 |
| python tools/publish_release.py --publish | 核对 GitHub 标签，上传和验证草稿，最后公开 |

## 准备候选

1. 在 tools/version.py 修改版本，运行 python tools/sync_versions.py。补齐本版变更说明，运行 python tools/collect_legacy_post_hashes.py 收录上一版官方安装器的生成后助手摘要。提交这些变更。
2. 选择尚未公开的版本号，为候选提交创建本地标签。从标签创建独立工作区，例如 git -c core.autocrlf=false worktree add --detach ../Cubemx_RCS_release_candidate vX.Y.Z。已有公开标签用于定位对应版本的源码。
3. 在同一个 Windows 用户会话准备 Python 3.11 或更高版本、.NET Framework、Git、GCC/G++/nm。native 和 release 还需要 CubeMX、STM32Cube F4 固件和 Keil ARM Compiler 6.22。CubeMX 和 Keil 路径可分别用 STM32CubeMX_PATH、RCS_KEIL_UV4 指定。运行 Python 时保留断言，清除 PYTHONOPTIMIZE。
4. 为 release 准备历史原版目录及当时保存的 SHA256 快照。RCS_BASELINE_ROOT 指向包含 foxmolika_CubeMX_0.3.7 等原版目录的父目录，默认是当前仓库的父目录。RCS_BASELINE_MANIFESTS 指向包含 original_037_SHA256.json 等快照的目录，默认是当前仓库的 build。已有 RCS_BASELINE_0037 可单独指定 0.3.7 目录。缺失文件会报出具体目录和清单。将可信的原件和已有快照一起离线归档，解压后可在新工作区复用。查看 release_baselines.py 中的版本列表可确认完整范围。

历史快照验证会读取原版文件并逐个比对摘要。当前 pack 内 C/H 与本次源码逐字节比较，当前固件与候选提交可达的上一正式版本标签比较，仅规范 CRLF/LF。如果新版本有意修改底层固件，需先评审并提交相应的基线判定及回归，随后冻结新标签。

## 运行与排错

运行 python tools/check.py --level release。每轮的 report.json 和各子进程的 stdout.log、stderr.log、step.json 位于 build/gate-runs/ 下，终端会打印实际路径。超时前已写出的字节仍保存在原始日志。报告中只有有长度上限的尾部。日志按步骤目录编号存放，同一脚本的不同调用各有文件。中文混合编码以原始字节为准，报告中的编码是尾部的解码结果。

release 在每步前后核对工作区状态与标签来源。被打包消费的报告和输入文件需由本轮产生并封存摘要。安装态报告会在卸载前核对真实编辑器的 SHA256，卸载通过后保存该摘要及卸载记录。编译输入清单记录实际源码、资源和工具的路径与摘要。打包时核对编辑器资源内的模板内容、suite 内嵌 editor/pack 及各产物摘要。

如只有最终打包失败，同一标签下可运行 python tools/check.py --level release --from tools/release.py。它会校验前序步骤、日志及证据原件和封存副本，把重试保存成新记录，并保留前序子进程明细。报告的 completed 包含打包，steps 只记录子进程，因此完整发布的 completed 比 steps 多一条。前序失败、源码改动或证据变化时重新运行完整 release。同一工作区的门禁和发布入口共享操作系统锁。

build/check-release.json 是最近一次被接受的门禁尝试摘要。失败轮、发布轮和冻结候选默认留存。可用 python tools/check.py --prune-successful 5 清理较早的成功 host/native 日志。各脚本在 build 下产生的其他测试工作目录由维护者按报告路径另行归档。原始日志及测试路径仅供本地排查，Keil 日志可能包含许可证信息。

## 冻结和公开

通过后，附件与 gate.json 一起放在 build/releases/vX.Y.Z/提交摘要/。正式附件由 SHA256SUMS.txt 指定。源码 ZIP 使用候选标签的 Git 归档，附 BUILD_PROVENANCE.json，打包和发布预检都会逐字节核验内容。同一标签和提交再次打包会提示已有冻结候选，可用只读预检查验。

推送候选源码与该新标签后，在同一工作区运行 python tools/publish_release.py。预检通过后执行 python tools/publish_release.py --publish 才会写入 GitHub。发布器解析远端真实 tag 提交，逐项核对草稿附件的名称、大小和 SHA256 后公开。已经公开的同版本会被拒绝。保存 build/github-publication.json 回执，公开后可下载单文件安装器并用 PowerShell 的 Get-FileHash 核对。
