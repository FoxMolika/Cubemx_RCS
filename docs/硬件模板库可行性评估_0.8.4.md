# 0.8.4 硬件模板库可行性评估

评估对象：`硬件模板库方案_0.8.4提案.md` 修订2；对照当前0.8.3.beta生成器及本地Togo final1队内驱动。本文仅为评估，没有修改程序、驱动或安装包，也没有开展新的实车验证。

## 结论

最终目标可实现，但修订2只能作为“驱动片段库与自动工程登记”的起点，尚未覆盖“GUI按模板新建硬件”。不能把参数配置、模板与实例区分、运行生命周期全部推迟到可选批3。

建议0.8.4交付“统一硬件管理 + 内置队内设备包 + 参数表单 + 新建模板向导 + 自动接入”。多实例运行可按驱动逐步开放，但数据模型应从第一版区分模板与实例。

一键导入的前提是：维护者先为该队内驱动整理一次设备包，包括真实依赖、函数映射、资源声明和调度约束。封装完成后，普通用户才能一键选用。不能承诺任意C库未经适配即可自动运行。

## 已核对的事实

- 实际航点动作编辑入口确为PhaseDialog→ActionProperties；五个动作文本框可以复用。
- HardwareSource是独立定位观测模型，只接受imu、tracking_encoder、external_pose，不能直接承载遥控、普通通信和执行器。
- APP_TICK在应用STOPPED、FAULT、FINISHED分支返回之后。只向这里添加采集函数，会在终止状态停止服务。
- 当前App初始化流程没有通用硬件初始化入口；只添加include并不能启动PWM、UART接收或驱动配置。
- 队内motor_2006声明1ms更新，直接定义HAL_CAN_RxFifo0MsgPendingCallback，并依赖can.h、chassis.h、pid.h、app_dbg.h。它不是完全独立的两个C/H文件。
- 队内servo_control明确说明SERVO_OK仅代表命令成功，不能当成实物到位；部分初始化会立即输出舵机目标。
- 现有单文件AtomicWrite与路线目录事务可以复用，但ProjectExport按顺序关联工程、写路线、登记Keil，不能据此宣称跨所有文件已有全局原子事务。

## 修订2需要调整的地方

| 项目 | 问题 | 最小调整 |
|---|---|---|
| GUI创建新硬件 | EXE内嵌固定索引没有用户模板保存入口；参数化被推迟 | 增加模板向导和可写用户模板目录，最少支持GPIO、PWM、UART/CAN句柄、ID、方向、限位、超时等有类型参数 |
| 硬件分类 | 把遥控/通信当定位源，会违反当前模型的类型与独立观测约束 | 通用DeviceInstance管理所有设备，具备定位能力的设备再关联HardwareSource |
| 执行器与传感器 | “执行器不能全程轮询，否则乱动”不成立 | 设备服务与动作命令分离；执行器可持续维护闭环，动作只发目标，Stop/Fault禁止新运动并执行安全处理 |
| 运行接入 | 缺初始化、使能、IRQ分发、停机和服务周期 | 生成统一硬件服务模块；接入App固定生命周期，不让用户每个设备手补main |
| 更新周期 | 所有驱动挂同一个APP_TICK不满足现有1ms驱动 | 模板声明周期、执行上下文与超时；根据约束生成服务或定时器分发，不以默认10ms代替1ms契约 |
| 来源验证 | none只插注释可能让默认恒真完成条件跳过动作 | 区分测试证据、实例配置完成和运行就绪；未就绪的必需设备明确阻止启动/动作，不静默跳过 |
| 不选设备逐字节不变 | 空USER CODE区仍会新增标记与DEFAULT/GENERATED摘要，故承诺不成立 | 真要保持字节一致，必须条件渲染且未选择时不新增序列化字段；否则明确改为行为与用户区兼容验收 |
| 多文件交付 | 单文件AtomicWrite不是跨目录、工程文件的全量回滚 | 先生成变更计划与预期hash，暂存、备份、提交并记恢复日志；回滚失败保留备份和准确错误 |
| 取消设备 | 只移除Keil登记，动作/状态机仍可能引用旧函数；配置头删除也可能破坏残余依赖 | 以实例ID检查所有引用；有依赖时阻止删除或明确同步移除；保留修改过的用户文件，不无条件删除配置头 |
| CAN冲突 | “同一CAN有电机”不等于所有报文都冲突 | 检查总线、发送报文/电流槽所有者及接收路由；同一0x200报文若无统一合帧器，第一版直接拒绝双发送者 |

可以保留硬件独立输出目录、SHA归属保护、Keil C/H登记和单独hardware.xml。记录设备配置的事实来源应是地图中的设备实例；hardware.xml记录实际交付，uvprojx是同步目标，不能反过来用工程树推断用户选择。

## 推荐的数据模型

| 对象 | 记录内容 |
|---|---|
| DeviceTemplate | 模板ID/版本、支持平台、C/H与公共依赖、参数定义、资源声明、生命周期、操作目录、测试证据 |
| DeviceInstance | 实例ID、名称、模板版本及摘要、参数值、外设绑定、是否配置完成 |
| DeviceOperation | 操作ID、参数、开始/执行中/完成/失败/取消语义；能绑定航点和业务状态机 |
| HardwareSource | 可选定位能力：观测轴、相对/绝对参考、读取函数、对齐、样本有效性 |
| hardware.xml | 已交付文件、公共依赖、引用计数、摘要与恢复信息，不替代地图配置 |

实例ID应跟随重命名保持不变，随地图保存、另存、撤销/重做和崩溃恢复。外部模板需固定版本/内容摘要；更新模板必须明确迁移，不能静默改变旧地图生成结果。

不要求第一版重构所有旧驱动为多实例。带全局变量的旧驱动可声明maxInstances=1并拒绝重复添加；可重入驱动才开放多个实例。这样能保留队内库，又避免以后重做整个数据模型。

## 用户看到的流程

### 一键引入已有队内硬件

硬件管理→添加设备→选择队内模板→填写/确认外设、接线和标定参数→检查配置→保存。

随后软件自动复制需要的驱动和适配层、生成配置、接入服务与回调、登记Keil。共享依赖只交付一次。原驱动符号尽量保留，通过薄适配层接入生成器，避免把队内代码全部改名或重写。

设备操作同时出现在航点动作和状态机的选择器。例如选“左夹爪→设角度”，填角度、完成方式与超时；按操作定义生成调用。若没有到位传感器，可以使用明确标注的时间等待，不能把指令返回成功当成到位证明。

### GUI手动创建新硬件

分为两个入口：

1. 从已有模板创建新实例，如右夹爪、第二路激光，编辑参数与资源绑定。
2. 创建可复用新模板：选基础类型→填写参数表单→导入已有C/H或填写驱动代码→映射初始化/服务/接收/操作/取消函数→声明资源→检查与测试→另存模板包。

GPIO/PWM等基础类型可以靠参数生成通用驱动；未知串口/CAN协议必须提供真实驱动或解析代码。GUI是编写、配置和复用驱动的入口，不能自动猜测未知协议。

内置模板只读；用户可以复制为个人模板修改。用户模板可导入/导出，安装修复和卸载不能顺带删除这些模板。导入时校验包内路径、文件大小、编码、重复ID及平台，不把任意路径写入用户工程。

## 运行结构

保持用户已有main固定入口：App_Init / App_Task。新增的硬件模块由生成器接入App，不要求每种设备修改main。

- 配置/初始化：检查资源、建立数据结构、启动所需接收；可能导致机构运动的使能或准备动作单独定义。
- 服务：按设备周期执行采集、缓存解析、闭环和状态维护。停止/故障后仍保留必要诊断与停机维护，但不发新运动指令。
- RX/定时器分发：一个HAL回调入口按句柄和帧ID路由，驱动不重复读取同一FIFO/字节流。已有用户回调冲突时明确拒绝静默覆盖。
- 命令与动作：由航点或业务状态机触发，返回运行中/完成/失败，取消时执行该设备真实的停止策略。
- 独立纠错：只有具备合适观测能力且已绑定/对齐的实例，才能成为纠错来源；没有设备时保持空模板。

## 0.8.4验收建议

1. 至少一个真实队内执行器与一个真实采集/通信驱动能完整引入：配置、服务、回调、C/H登记均自动完成。
2. 执行器操作在航点和状态机两个入口都能选用，开始、完成、超时、取消语义一致。
3. 用户不改生成器源码、不重新编译EXE，即可在GUI新建GPIO/PWM模板，导出后重新导入并使用。
4. 用户新模板可以导入既有协议驱动，函数映射错误、未声明依赖、资源冲突有明确诊断。
5. 驱动要求1ms而选定调度不能满足时拒绝配置，不能以10ms调用冒充接入。
6. CAN/UART接收、Stop/Fault后的必要服务、重复初始化、回调冲突有真实生成代码测试。
7. 同名实例、单实例驱动重复添加、共享依赖、被引用设备取消、手改驱动文件均有保护。
8. 多文件提交中断、外部改动、回滚失败能恢复或保留现场，不伪报“原工程完全未变”。
9. 不选硬件的旧地图回归通过；新设备信息参与revision、预构建检查、撤销和恢复。
10. 新电脑安装后可使用内置库；个人模板升级后保留；原生CubeMX/Keil验收与实车证据分别记录。

## 实施顺序与工作量判断

先确定设备包与实例契约，并挑一个真实舵机和一个真实串口/CAN驱动做端到端；再补模板创建向导、导入导出与保护测试。片段插入可以作为内部里程碑，但不能把“仍需手动复制驱动、添加回调”称为最终一键交付。

提案的8～12人日只能视为固定少量设备、已有驱动封装完成且不含GUI模板创作的估计。最终目标增加参数表单、用户模板、生命周期、回调与依赖适配，不能直接沿用该工期。应在两个真实设备的端到端试做后，再按模板数量与旧驱动耦合程度估算。
