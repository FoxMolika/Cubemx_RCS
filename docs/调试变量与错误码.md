# 调试变量与错误码（0.8.4.beta）

本文件回答三件事：插件生成的状态**在哪**、**叫什么**、**取值代表什么**。
所有名称都取自生成目录 `Application/foxmolikaRoute/`，可直接填进 Keil 的 Watch 窗口。

---

## 0. 先看这个：快照 `g_dbg`

生成器在 `rcs_app_task.h` 声明、在 `rcs_app_task.c` 每轮 `App_task()` 刷新一个只读快照。
Watch 里**只加一个 `g_dbg`**，展开即可看全，不必逐个找变量，也不受优化等级影响：

```c
typedef struct {
    volatile uint8_t  app_state, app_fault, feedback_fault, chassis_fault;
    volatile uint8_t  nav_fault, machine_fault, port_fault, holding, ready;
    volatile float    pose_x, pose_y, pose_yaw;
    volatile uint32_t fault_tick, feedback_sequence, rx_count;
    volatile uint32_t loop_ms, loop_max_ms;
    volatile uint32_t gap_us_last, gap_us_max;
    volatile uint8_t  dwt_ready;
    volatile int32_t  wheel_pending[4];
    volatile uint32_t wheel_age_ms[4];
} foxmolika_debug_t;
extern volatile foxmolika_debug_t g_dbg;
```

### 0.1 照抄清单

Keil 的 Watch 窗口支持一次粘贴多行。**新固件**（含 `g_dbg`）照这份贴，
顺序就是排查顺序：

```text
g_dbg
g_dbg.app_state
g_dbg.app_fault
g_dbg.port_fault
g_dbg.feedback_fault
g_dbg.chassis_fault
g_dbg.nav_fault
g_dbg.machine_fault
g_dbg.rx_count
g_dbg.feedback_sequence
g_dbg.gap_us_max
g_dbg.gap_us_last
g_dbg.loop_max_ms
g_dbg.loop_ms
g_dbg.wheel_age_ms
g_dbg.dwt_ready
g_dbg.ready
g_dbg.holding
g_dbg.pose_x
g_dbg.pose_y
g_dbg.pose_yaw
```

嫌多就只留前 6 行；`g_dbg` 本身展开也能看到全部字段。
还要看真正锁存的那一刻，直接加文件级静态：`\rcs_feedback_port.c\g_fault`。

### 0.2 旧固件（还没有 `g_dbg`）

车上是重装前的构建时，`g_dbg` 不存在，只能用这三个 static 加访问函数：

```text
g_sequence
g_fault
g_wheels[0].tick
App_task_Fault()
App_task_FeedbackFault()
```

`g_sequence` 停在 8、`g_fault` = 3 就是你现在这个现象。要看 `rx_count` / `gap_us_max`
必须先重新 `Generate Code`、编译、烧录。

### 0.3 字段对照

| 字段 | 对应 | 说明 |
|---|---|---|
| `app_state` | `App_task_State()` | 0–6，见 7.1 |
| `app_fault` | `App_task_Fault()` | 首次故障，0–7，见 7.2 |
| `feedback_fault` | `App_task_FeedbackFault()` | 应用层抓到的**首次**故障快照，0–8；启动等待期间可能仍是 0 |
| `port_fault` | `rcs_feedback_port_fault()` | **实时**端口故障，0–8；判断锁没锁存看这个 |
| `chassis_fault` | `App_task_ChassisFault()` | 0–7，见 7.4 |
| `nav_fault` | `App_task_NavFault()` | 0–13，见 7.5 |
| `machine_fault` | `App_task_MachineFault()` | 0–5，见 7.6 |
| `holding` / `ready` | `App_task_Holding()` / `IsReady()` | 1 = 是 |
| `pose_x/y/yaw` | `g_pose_x/y/yaw` | 应用层位姿（米、弧度） |
| `fault_tick` | `App_task_FaultTick()` | 首次故障时刻 |
| `feedback_sequence` | `g_sequence` | 累计**被接受**的帧数；静止 4 电机应 ≈4000/秒 |
| `rx_count` | `g_rx_count` | 进入收帧函数的次数，**含锁存后被丢弃的帧** |
| `loop_ms` | — | 上一次 `App_task()` 到本次的间隔 |
| `loop_max_ms` | — | 上电以来的最大 `loop_ms`；大于 `RCS_PERIOD_MS` 即有阻塞 |
| `gap_us_last` | `g_gap_us_last` | 最近一次同轮帧间隔（微秒，DWT 周期计数） |
| `gap_us_max` | `g_gap_us_max` | 本次启动以来最大空窗（微秒）；5 ms 判据对应 5000 |
| `dwt_ready` | `g_dwt_ok` | 1 = 微秒读数可信；0 = 主机测试或无 DWT |
| `wheel_pending[i]` | `g_wheels[i].pending` | 该轮未消费的原始增量 |
| `wheel_age_ms[i]` | `HAL_GetTick() - g_wheels[i].tick` | 该轮距上次收帧的毫秒数；`0xFFFFFFFF` = 从未收到 |

### 0.4 `gap_us_max` 判读

| `gap_us_max` | 含义 |
|---|---|
| 900–1300 | 正常（C620 1 kHz + 中断抖动） |
| 2000–5000 | 接近上限，主循环偶有停顿 |
| >5000 | 触发 `AMBIGUOUS_GAP` 的那次空窗；数值越大越像"中断没跑" |
| 0 且 `dwt_ready=0` | 微秒诊断不可用（主机测试环境） |

### 0.5 `rx_count` 与 `feedback_sequence` 的差值

| 现象 | 含义 |
|---|---|
| 两者都涨 | 正常，帧在被接受 |
| `rx_count` 涨、`feedback_sequence` 不涨 | 帧**到了**，但被故障锁存丢弃 → 查故障码 |
| 两者都不涨 | 帧**没到** → 查 CAN 中断、过滤器、接线 |

刷新时机是每次 `App_task()` 调用，**不受 10 ms 应用分频限制**，所以 `wheel_age_ms`
能直接反映反馈分发节奏：静止时应稳定在个位数，持续大于 5 就会触发
`RCS_FEEDBACK_AMBIGUOUS_GAP`（见 8.1）。

## 1. 变量分布

插件生成两类东西（外加第 0 节的快照）：

| 类别 | 位置 | 特点 |
|---|---|---|
| 访问函数 | `rcs_app_task.h` 声明的 `App_task_*()` | 非静态，必定能 Watch；但**只在调试器刷新时求值** |
| 内部状态 | 各 `.c` 的 `static` 变量 | 内存里实时变，适合跑动中观察；开高优化可能被优化掉 |

| 文件 | 内容 |
|---|---|
| `rcs_app_task.c` | 应用状态机、首次故障快照、位姿、驻坡 |
| `rcs_feedback_port.c` | C620 逐帧角度解绕、新鲜度、帧间隔判据 |
| `rcs_hal.c` / `rcs_control.h` | 底盘控制器 `g_controller` |
| `rcs_can_port.c` | CAN 句柄绑定 |
| `rcs_nav.c` / `rcs_nav.h` | 导航器 `g_nav`、阶段、航点 |
| `machism.c` / `machism.h` | 用户状态机与故障码 |

### 2.1 访问函数

| 表达式 | 返回类型 | 含义 |
|---|---|---|

| `App_task_MachineFault()` | `int` | 状态机故障码（见 7.6） |

| `App_task_Holding()` | `int` | 1 = 正在坡道驻坡保持 |

## 3. 反馈端口（`rcs_feedback_port.c`）

| 变量 | 类型 | 含义 |
|---|---|---|
| `g_fault` | `rcs_feedback_fault` | **实时**故障码；锁存后不再处理任何帧（见 7.3） |
| `g_initialized` | `uint8_t` | 配置是否合法；0 = 参数组合被拒 |
| `g_fresh` | `uint8_t` | 位掩码，bit0–3 = W0–W3 有新帧未消费 |
| `g_sequence` | `uint32_t` | 累计有效帧数，**判断分发是否在跑的最佳指标** |
| `g_wheels[0..3]` | 结构数组 | 每轮状态，见下表 |

`g_wheels[i]` 字段：

| 字段 | 类型 | 含义 |
|---|---|---|
| `.angle` | `uint16_t` | 最近一次原始角度，0–8191 |
| `.pending` | `int32_t` | 自上次被应用消费以来的累计增量 |
| `.tick` | `uint32_t` | 最近一次**被消费**的 `HAL_GetTick()` |
| `.seen` | `uint8_t` | 是否已建立基准 |

常用观察式：

| 表达式 | 正常值 | 说明 |
|---|---|---|
| `HAL_GetTick() - g_wheels[0].tick` | ≈1 ms | 越大说明分发越慢；> `RCS_FEEDBACK_MAX_GAP_MS` 就会锁存 |
| `g_sequence` 每秒增量 | ≈4000 | 4 电机 × 1 kHz；只有一两百 = 消费端慢 |
| `g_fresh` | 0 或 0x0F | 长期 0 且 `g_sequence` 不涨 = 没收到帧 |

## 7. 错误码总表

Watch 里只显示数字，下面是对照。

### 7.1 `rcs_app_state`（`App_task_State()`）

| 值 | 名称 | 含义 |
|---|---|---|
| 0 | `RCS_APP_NOT_READY` | 未初始化或不满足启动条件 |
| 1 | `RCS_APP_READY` | 可启动 |
| 2 | `RCS_APP_ARMING` | 已申请解锁，等待真实反馈 |
| 3 | `RCS_APP_RUNNING` | 路线执行中 |
| 4 | `RCS_APP_FINISHED` | 路线完成 |
| 5 | `RCS_APP_FAULT` | 故障，不会自恢复 |
| 6 | `RCS_APP_STOPPED` | 已显式停止 |

### 7.2 `rcs_app_fault`（`App_task_Fault()`）

| 值 | 名称 | 含义 | 接着看 |
|---|---|---|---|
| 0 | `RCS_APP_ERROR_NONE` | 无故障 | — |
| 1 | `RCS_APP_ERROR_CONFIGURATION` | 配置非法（PID 全零、周期矛盾等） | `app_configuration_ok` 的分支 |
| 2 | `RCS_APP_ERROR_INITIALIZATION` | 初始化失败 | `g_initialized`、`g_can` |
| 3 | `RCS_APP_ERROR_FEEDBACK` | 反馈端口故障 | `App_task_FeedbackFault()` → 7.3 |
| 4 | `RCS_APP_ERROR_CHASSIS` | 底盘故障 | `App_task_ChassisFault()` → 7.4 |
| 5 | `RCS_APP_ERROR_NAVIGATION` | 导航故障 | `App_task_NavFault()` → 7.5 |
| 6 | `RCS_APP_ERROR_MACHINE` | 状态机故障 | `App_task_MachineFault()` → 7.6 |
| 7 | `RCS_APP_ERROR_HARDWARE` | 硬件设备故障 | 硬件设备的 `.fault` |

### 7.3 `rcs_feedback_fault`（`App_task_FeedbackFault()` / `g_fault`）

| 值 | 名称 | 含义 | 典型原因 |
|---|---|---|---|
| 0 | `RCS_FEEDBACK_OK` | 正常 | — |
| 1 | `RCS_FEEDBACK_BAD_CONFIG` | 参数组合被拒 | `MAX_GAP` 超过 `rpm*(gap+1) < 30000` |
| 2 | `RCS_FEEDBACK_STALE` | 某轮超过 `RCS_FEEDBACK_SAMPLE_TIMEOUT_MS` 没新帧 | 断线、驱动器掉电、过滤器漏 ID |
| 3 | `RCS_FEEDBACK_AMBIGUOUS_GAP` | **相邻帧间隔超过 `RCS_FEEDBACK_MAX_GAP_MS`** | 分发被阻塞（见 8.1） |
| 4 | `RCS_FEEDBACK_BAD_ANGLE` | 原始角度 ≥ 8192 | 帧解析错误、ID 串位 |
| 5 | `RCS_FEEDBACK_DELTA_RANGE` | 单帧增量超出可能转速或累计溢出 | 转速超配置、编码器跳变 |
| 6 | `RCS_FEEDBACK_FIFO_OVERRUN` | FIFO0 溢出 | 纯轮询且周期 > 0.75 ms |
| 7 | `RCS_FEEDBACK_CAN_BUS_OFF` | 总线关闭 | 接线、终端电阻、驱动器故障 |
| 8 | `RCS_FEEDBACK_CAN_RX_FAILED` | 取帧失败或通知未激活 | `HAL_CAN_ActivateNotification` 失败 |

`RCS_FEEDBACK_MAX_GAP_MS` 默认 `15000 / RCS_MAX_MOTOR_RPM`：3000 rpm 时为 **5 ms**，
正好是"最大转速下转四分之一圈"。超过就无法唯一还原圈数，所以端口宁可报错也不猜。

## 8. 排查路径

### 8.1 "车不动，停在 READY"

典型组合：`app_state` = 1、`port_fault` = **3**、`rx_count` 在涨、`feedback_sequence` 不动。

含义：反馈端口锁存了一次，之后**永久丢弃所有帧**，`RCS_Arm()` 再也拿不到四轮新鲜反馈，
应用就停在 READY 反复失败。调高阈值只是让判据不触发，不是修好。

#### 根因 A：毫秒量化误报（0.8.4 已修）

`RCS_FEEDBACK_MAX_GAP_MS` 是整数毫秒：`15000 / 13680` 取整后是 **1 ms**。
而 C620 的帧距是 **1035 µs**，用 `HAL_GetTick()` 量出来的差值是 1 或 2 ms——
跨 tick 边界时量成 2 ms，超过 1 ms 上限，直接锁存。

这不是"分发慢"，是**判据的分辨率和被测量同一量级**。0.8.4 起改为微秒窗口：

| 版本 | 判据 | 13680 rpm 的窗口 | 1035 µs |
|---|---|---|---|
| 0.8.3.x | `gap(ms) > 1` | 1000 µs | 边界抖动时误报 |
| 0.8.4 | `gap_us > RCS_FEEDBACK_MAX_GAP_US` | **1644 µs** | 通过 |

窗口按"最大转速下 3/8 圈"换算（`RCS_FEEDBACK_GAP_COUNTS` = 3072），
给半圈歧义留 1/8 圈余量，同时比 1 ms 多出 60% 容差。
没有 DWT 的平台退回原毫秒判据，行为不变。

#### 根因 B：真的有空窗

| 判据 | 含义 | 修法 |
|---|---|---|
| `gap_us_max` ≫ 窗口（如 >5 ms） | 某一段真的没人取帧 | 找阻塞；或中断没使能 |
| `loop_max_ms` ≥ `RCS_PERIOD_MS` | 主循环停过 | 挪走阻塞（`rcs_hw_service`、阻塞 UART、`HAL_Delay`、Flash、OLED） |
| `rx_count` 也不再涨 | 帧没到 | 查 NVIC、过滤器、ID、接线、供电 |
| `port_fault` = 6 | FIFO 溢出 | 回调没人定义，或通知没激活 |
| `port_fault` = 7 | 总线关闭 | 接线、终端电阻、驱动器 |

#### 确认顺序

1. 先看 `port_fault`（不是 `feedback_fault`——后者是应用层快照，启动等待期间可能仍是 0）；
2. 再看 `gap_us_max`：落在 1000–1200 是正常；略超窗口是量化/抖动；远超就是真停顿；
3. 最后看 `loop_max_ms` 与 `rx_count` 增速，区分"主循环慢"和"帧没到"。

修好之后把 `RCS_FEEDBACK_MAX_GAP_MS` 的覆盖值删掉，回默认。

#### 为什么"调高就能动"是假象

判据一放宽，`possible`（单帧最大可接受增量）也会跟着放大，启动瞬间增量接近 0，
自然就"能动了"。但车跑起来后超过半圈，12 位单圈角度无法还原跨了几圈，
端口会从"报错"变成"猜"——症状变成位置整圈丢失，比现在难查得多。

最直接的验证：静止上电后看 `g_dbg.rx_count` **每秒增量**。4 电机 × 1 kHz 应约 4000；
如果只有个位数，问题就在接收侧，不在判据。

#### 0.8.4.beta 的兜底

`rcs_can_port.c` 现在提供一个**弱定义**的 `HAL_CAN_RxFifo0MsgPendingCallback`：

- 统一分发器（`rcs_hw_callbacks.c`）在时，强定义覆盖它，行为不变；
- 它没被链接进来时，这个弱定义仍会在中断里排空 FIFO；
- 只有连 NVIC 都没开，才会真正退化成主循环轮询。

所以"硬件分发器缺失"不再是"5 ms 空窗"的直接原因；剩下要查的就是 NVIC 与主循环阻塞。

## 9. Watch 使用注意

1. **函数不实时**：`App_task_*()` 在 Watch 里只在调试器刷新时求值。
   连续观察请直接 watch `g_dbg`（第 0 节），并打开 **Debug → Periodic Window Update**。
2. **静态变量重名**：`g_can`、`g_initialized` 等在多个文件里都有。重名时用
   `文件名\变量名`，或从 Symbol 窗口拖入。
3. **优化等级**：当前按 -O0 生成，`static` 可见；开 -O1 以上时小变量可能被寄存器化，
   Watch 显示 `<not in scope>`。`g_dbg` 是 `volatile` 全局量，升优化后仍可读，优先用它。
4. **不要在 Watch 里改值**：`g_fault`、`g_first_fault` 手工清零会掩盖真实故障，
   而且看门狗仍在运行；要恢复请走 `App_task_Stop()` → `App_task_Init()` 的正常路径。
